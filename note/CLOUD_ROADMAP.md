# 3媒体noteクラウド運用：現在の段階と導入手順

## 実装済み
- `scripts/plan_note_queue.py`: 3媒体のmanifestとarticle.mdを読み取り、投稿候補・スキップ・重複・修正を分類する。**読み取り専用**。
- `.github/workflows/note-queue-dry-run.yml`: 3リポジトリをCloud GitHub Actionsにcheckoutし、地域・ガチャの週次生成処理を走らせ、分類結果JSONをartifactに保存する。
- GitHub Actionsはnoteログイン・投稿・外部公開を一切しない。

## 実行
Actions > Three-site note queue dry-run > Run workflow。
結果はArtifactsの `note-queue-dry-run` からダウンロードする。
ジョブの成功はnote投稿成功を意味しない。

## 注意：毎週の差分検出
`note/place-snapshot.json` と `note/store-snapshot.json` は前回状態が必要。
ワークフローは毎回新しいチェックアウトで動くので、現段階ではスナップショットが永続化されない。
つまり、ここでの実行は初回基準作成と形式検証のみ。**週次差分検出の本番運用ではない**。
本番ではOracle VMの専用ディレクトリに前回スナップショットと投稿状態を保持し、バックアップ・排他ロックを実装する。
状態の自動GitHub pushは本番検証まで行わない。
また、地域情報の独立した公開URLと公式イベント情報の審査が完了するまでは地域情報の記事公開を行わない。

## 次の実装
1. 取得済みデータと前回スナップショットを永続化する独立したOracle VMジョブ。途中失敗の場合スナップショットを進めない。
2. 投稿候補のschema/出典を検証し、投稿済みのnote記事ID・URLを保存するSQLiteデータベース。
3. note投稿バッチv0.3のソース所在と利用方法を確認してからクラウドへ移植。現時点でソースは3リポジトリ内で確認できていない。
4. 初回ログイン、セッション保存（VM上、権限限定、暗号化）、下書き作成、投稿結果照合、例外通知の順で実地検証。
5. 予定時刻を確定してから週次スケジュールを有効化。公開自動化は下書き成功と規約面を確認してから別途判断する。

## セキュリティ
- GitHub ActionsにnoteアカウントのCookie、パスワードやセッションを渡さない。
- 自動ブラウザ操作で認証を迂回しない。手動追加認証が必要な場合は停止する。
- 1媒体・1週1記事を既定とし、既存記事との差分は自動で追加投稿せず要確認扱いとする。
